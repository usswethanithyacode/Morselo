# Morselo MongoDB Architecture: Embedding vs. Referencing Relationships

This document outlines the **MongoDB Schema Design** for Morselo using **Mongoose**, focusing on the distinction and implementation of **Embedded Documents** versus **Referenced Documents (Normalized Data)**.

---

## 1. Overview & Architectural Separation

Morselo utilizes **MongoDB Atlas** with **Mongoose** for managing flexible culinary content (users and recipe documents).

| Collection | Model File | Relationship Pattern | Purpose |
|---|---|---|---|
| `recipes` | [`server/models/Recipe.js`](file:///c:/Users/usswe/OneDrive/Desktop/Morselo/server/models/Recipe.js) | **Embedding** (`ingredients`, `steps`) | Stores independent recipe documents with tightly coupled sub-arrays. |
| `users` | [`server/models/User.js`](file:///c:/Users/usswe/OneDrive/Desktop/Morselo/server/models/User.js) | **Referencing** (`savedRecipes` $\rightarrow$ `Recipe._id`) | Stores user accounts with references to bookmarked recipes. |

## 2. Embedding vs. Referencing in MongoDB

MongoDB supports two primary strategies for modeling document relationships:

```
                  ┌──────────────────────────────────────────────┐
                  │          MongoDB Relationship Types          │
                  └───────┬──────────────────────────────┬───────┘
                          │                              │
             ┌────────────▼───────────┐    ┌─────────────▼──────────┐
             │       Embedding        │    │      Referencing       │
             │ (Denormalized Objects) │    │  (Normalized ObjectIds)│
             └────────────┬───────────┘    └─────────────┬──────────┘
                          │                              │
     • Tightly coupled data               • Independent lifecycles
     • 1-to-few bounded arrays            • 1-to-many / many-to-many
     • Read/written together              • Shared across entities
     • Fast single-document read          • Prevents duplicate data
```

---

## 3. What is Embedded in Morselo

In [`server/models/Recipe.js`](file:///c:/Users/usswe/OneDrive/Desktop/Morselo/server/models/Recipe.js), ingredients and cooking steps are **embedded directly** as sub-arrays inside the Recipe document:

```javascript
const recipeSchema = new mongoose.Schema(
    {
        name: { type: String, required: true, trim: true },
        description: { type: String, trim: true },
        // Embedded array: tightly coupled to this specific recipe
        ingredients: { type: [String], required: true },
        // Embedded array: ordered list of steps
        steps: { type: [String], required: true },
    },
    { timestamps: true }
);
```

### Why Embedding is Used for Ingredients & Steps:
- **Atomicity**: When fetching or saving a recipe, its ingredients and steps are always needed together in a single atomic read/write.
- **Bounded Size**: A recipe typically has 5–25 ingredients and steps, well within MongoDB's 16MB document size limit.
- **Simplicity**: No separate database roundtrips are needed to assemble the complete recipe.

## 4. What is Referenced in Morselo

In [`server/models/User.js`](file:///c:/Users/usswe/OneDrive/Desktop/Morselo/server/models/User.js), a user's bookmarked/saved recipes are **referenced by ObjectId**:

```javascript
const userSchema = new mongoose.Schema(
    {
        email: { type: String, required: true, unique: true, trim: true, lowercase: true },
        username: { type: String, required: true, trim: true },
        passwordHash: { type: String, required: true },
        role: { type: String, enum: ['user', 'admin'], default: 'user' },
        // Referencing: Stores array of Recipe ObjectIds referencing the 'Recipe' model
        savedRecipes: [
            {
                type: mongoose.Schema.Types.ObjectId,
                ref: 'Recipe',
            },
        ],
    },
    { timestamps: true }
);
```

---

## 5. Why Recipe is Referenced Instead of Embedded in User

1. **Independent Lifecycle**: Recipes exist independently of any individual user. They are created, edited, shared, or generated by AI separately.
2. **Data Consistency (Single Source of Truth)**: If a recipe's ingredients or cooking steps are updated, referencing ensures all users who saved that recipe automatically see the updated version without requiring synchronization across multiple user documents.
3. **Preventing Document Growth & Bloat**: If full recipe objects were embedded inside `User.savedRecipes`, a user saving hundreds of recipes would cause unbounded growth of the User document, potentially risking MongoDB's 16MB per-document limit.
4. **Memory & Bandwidth Efficiency**: Basic user operations (e.g., login, profile check) only load lightweight user fields and ObjectIds without loading massive nested recipe data unless explicitly requested via `populate()`.

## 6. How Mongoose `populate()` is Used

When an authenticated client requests their saved recipes, the backend dynamically resolves the referenced ObjectIds into full `Recipe` documents using Mongoose `populate('savedRecipes')`.

### Implementation ([`server/server.js`](file:///c:/Users/usswe/OneDrive/Desktop/Morselo/server/server.js)):

```javascript
app.get('/api/users/saved-recipes', authenticateToken, async (req, res) => {
    try {
        // Query user and dynamically join referenced Recipe documents
        const user = await User.findById(req.user.id).populate('savedRecipes');
        if (!user) {
            return res.status(404).json({ error: 'User not found.' });
        }
        
        // Filter out any null entries (if a referenced document was deleted)
        const validRecipes = (user.savedRecipes || []).filter(Boolean);
        return res.status(200).json(validRecipes);
    } catch (error) {
        console.error('Error fetching user saved recipes:', error);
        return res.status(500).json({ error: 'Could not fetch saved recipes.' });
    }
});
```

---

## 7. Referential Integrity & Cascade Cleanup

When an independent recipe is deleted via `DELETE /api/recipes/:id`, the backend automatically removes the deleted recipe's `_id` from all user `savedRecipes` arrays:

```javascript
// Remove deleted recipe ID from all users' savedRecipes reference arrays
await User.updateMany(
    { savedRecipes: id },
    { $pull: { savedRecipes: id } }
);
```

This prevents dangling/orphaned ObjectId references.

## 8. API Endpoints for Referenced Relationships

| Method | Endpoint | Auth Required | Description |
|---|---|:---:|---|
| `GET` | `/api/users/saved-recipes` | `Bearer <token>` | Returns the user's populated list of saved recipe documents via `.populate('savedRecipes')`. |
| `POST` | `/api/users/saved-recipes/:recipeId` | `Bearer <token>` | Adds a Recipe ObjectId to `user.savedRecipes` (using `$addToSet` to prevent duplicate references). |
| `DELETE` | `/api/users/saved-recipes/:recipeId` | `Bearer <token>` | Removes a Recipe ObjectId reference from `user.savedRecipes` (using `$pull`). |
| `DELETE` | `/api/recipes/:id` | Public / Admin | Deletes a recipe document and cascades reference cleanup across all users. |
| `GET` | `/api/recipes` | Public | Returns all standalone recipe documents. |
